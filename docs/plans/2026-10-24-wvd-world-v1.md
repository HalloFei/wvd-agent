# WVD World v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a Coopanion extension that runs the FFXI 4F chest route unattended: open the map, automove to each chest, disarm the QTE, fight with auto-battle, exit.

**Architecture:** One Cortico World package, this repository's root, loaded into Coopanion by `link:`. A child process owns every Win32 call; the World runs a 10 Hz loop that captures the window, parses the screen, and either acts or escalates to Coo.

**Tech Stack:** TypeScript (Node 22), koffi for Win32, vitest, pnpm. No new runtime dependencies beyond what Coopanion already ships.

**Spec:** `docs/specs/2026-10-23-wvd-world-design.md`, `docs/specs/2026-10-24-chest-policy-design.md`, `docs/specs/2026-10-24-navigation-design.md`

## Global Constraints

- Every input asserts the game window is foreground first; refuse otherwise. No exceptions.
- Raw BGRA never crosses the child boundary: encode JPEG in the child.
- Coordinates are device pixels of the 1920×1080 window; convert at the boundary, once.
- No network in tests. Fixtures live under `testdata/`.
- The World imports only `cortico/core/types.ts` and its own modules; no Coopanion internals.
- A module returns a typed failure; it never throws into the loop.
- Automove, chest and QTE constants come from the specs, never invented here.

  `corepack` cannot bootstrap it here (it fails to verify the npm signing key), so pnpm comes from
  `npm i -g pnpm@11.28.6`.
- `Coopanion/node_modules` exists: `pnpm install` has been run in `Coopanion/`. Linking a World
  needs the app's own installed toolchain, so this precedes Task 1 step 5.
- `Wizardry Variants Daphne` is installed (Steam, app 2379740) and launchable by the operator.
  Nothing in Tasks 1–9 starts it themselves.
- `ffmpeg` is on PATH. Only the replay harness (Task 9) needs it, and it skips without it.

## Contracts

Binding: `docs/specs/2026-10-24-contracts.md`. Every task below implements or consumes those
declarations, and `src/contracts.ts` mirrors them verbatim. A change to a
contract is a change to both files in the same commit; no task may invent a name that is not there.

## Review Focus

- **Window loses focus mid-action** → the next input must refuse, not click into another app.
- **Black or uniform frame** → perception must report `unknown`, never a screen with high confidence.
- **Combat interrupts automove** → hand off to battle, never resume the walk blindly afterwards.
- **QTE bar unparseable** (no cursor, no zone pair) → refuse to tap; a miss costs willpower.
- **Opener refuses** (low willpower) → fall through to the next opener rather than retrying the same one.
- **A module is replaced** (JPEG source swapped, map parser rewritten) → no other module's code changes; only the composition root's wiring.

### Task 2: Engine child — capture and foreground guard

**Files:**
- Create: `src/engine/protocol.ts`, `src/engine/win32.ts`, `src/engine/child.ts`
- Test: `tests/engine.test.ts`

**Interfaces:**
- Consumes: `Frame` from `contracts.ts`.
- Produces: `EngineRequest` / `EngineReply` exactly as contracts §5, `startEngine(): ChildProcess`, and `Win32Capture implements FrameSource` whose `capture(): Promise<Frame>` returns JPEG bytes with `atMs` taken before the capture. The child also registers the global stop hotkey (`stopHotkey`, default `Ctrl+Alt+W`) with `RegisterHotKey` and reports `{ kind: 'stopHotkey' }` upward; a `foreground: false` reply is the engine's `rejected`, so `sendInput` returns `{ ok: false, reason: 'rejected', detail: 'not-foreground' }` — the contracts know no other failure name.

- [ ] **Step 1: Write the failing test** — protocol round-trips a `capture` request; a fake engine reply with `foreground: false` makes `sendInput` reject with `NotForeground`.
- [ ] **Step 2: Run it** — expect failure.
- [ ] **Step 3: Implement** the protocol codec, the koffi bindings (`PrintWindow`, `GetForegroundWindow`, `SendInput`, `SetCursorPos`, `RegisterHotKey`), the child loop, and its message pump so the hotkey is serviced while capture runs.
- [ ] **Step 4: Run the test** — expect PASS.
- [ ] **Step 5: Commit** — `feat(wvd): a child process that captures the window and guards input`.

### Task 4: Map perception

**Files:**
- Create: `src/perception/map.ts`
- Test: `tests/map.test.ts`

**Interfaces:**
- Consumes: `Frame`.
- Produces: `MapPerceiver implements Perceiver` whose `observe(frame)` returns a `dungeonmap` observation carrying `MapState`, or `unknown` below its confidence floor. `readMap(frame): MapState | null` is its internal parser. Dimensions come from `frame.width`/`frame.height`, never constants.

- [ ] **Step 1: Write the failing test** — against `testdata/nav-1024-0213/map.png`, `readMap` returns `floorTitle === 'B1F -巨坑-'`, `player` equal to `{x:20,y:14}` as that frame's readout says, at least three `chest` icons, and at least one `hazard`; against `testdata/nav-1024-0213/minimap-and-hud.png` it returns `null` — the HUD alone is not a map, and a parser that mis-reads a HUD is worse than one that refuses.
- [ ] **Step 2: Run it** — expect failure.
- [ ] **Step 3: Implement** title detection, the `X: n Y: n` read, and icon matching against templates cropped from the same frame. Geometry from `research-map-parser.md`: tiles are 36.0 px square, and the map canvas **scrolls** between captures (measured 21, 72 and 210 px on one floor), so nothing may anchor to an absolute origin — the click transform is `chevron + ((x_t − x_p)·36, −(y_t − y_p)·36)`, Y inverted. Digits are 12 px at a fixed rect; only 7 of 10 glyphs have a sample, so an unknown digit returns `null`, never a guess. `haken` is not identifiable in any fixture and must not be emitted.
- [ ] **Step 4: Run the test** — expect PASS.
- [ ] **Step 5: Commit** — `feat(wvd): read the dungeon map`.
